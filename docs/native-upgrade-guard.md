# Native CLI upgrade guard

`CODEX_CLI_PATH` is installed as a small Win32 GUI-subsystem bootstrap. It is not a Node, batch, or PowerShell launcher. At startup it finds the desktop's official Codex executable from an ancestor `OpenAI.Codex_<package>...\app\Codex.exe` image, then uses that package's `app\resources\codex.exe`. If ancestry cannot be resolved, it finds the newest installed package. It never treats the inherited `CODEX_CLI_PATH` as the official executable and refuses to recurse into itself.

The bootstrap selects the isolated patched CLI only when `compatibility.json` has schema 1 and matches the official executable SHA-256, full `codex-cli --version`, exact Windows package version, the patch's compiled-in approved SHA-256, and a successful `app-server-initialize` probe receipt. The patch must be a regular file under `%CODEX_HOME%\router-runtime` (or `%USERPROFILE%\.codex\router-runtime`). Any missing, stale, malformed, or mismatching evidence selects official Codex immediately and writes a local `upgrade-status.json` with a Chinese disabled reason. Status is separate from stdout/stderr so app-server JSON-RPC remains clean.

`native-bootstrap-install.mjs` builds an environment plan that points to a content-addressed bootstrap under `<CODEX_HOME>\router-runtime\bootstrap\<sha256>.exe`. Apply copies it atomically from the plugin's packaged bootstrap, then changes environment values using compare-before-set. The returned journal snapshot includes the prior bootstrap bytes; rollback restores/removes the executable only if its current hash still matches the installed bytes, and restores environment values only if they still match the transaction. A non-WindowsApps user-selected `CODEX_CLI_PATH` without an owned receipt is preserved by refusing the plan.

For an approved patch, the bootstrap starts it with inherited standard handles and original arguments, hidden-window flags, and waits up to 1.8 seconds. If process creation fails or the process exits during that startup grace period, it records disabled status and starts the official CLI with the original arguments. This is an early process-failure fallback; it cannot recover from a patched app-server that remains alive but later rejects the desktop's initialize request. The install-time initialize probe and exact binary/package binding are therefore required before selecting a patch.

## Status contract

`scripts/native-upgrade-guard.mjs` exports pure selection/status helpers. Status is `{state: "healthy"|"repaired"|"disabled", reason, repairAttempted, updatedAt}`; no credentials or identity material are stored. The native bootstrap writes `healthy` when a verified patch is selected and `disabled` when it falls back. The routing/settings layer must consume this status to disable only the native child role and surface the Chinese reason. This module does not implement a Windows toast or UI notification; it must not be presented as end-to-end notification until that consumer is wired.

## Evidence and limits

- The checked-in bootstrap was built locally with MinGW GCC (`-municode -mwindows -O2 -lbcrypt -lshell32`), source `native/bootstrap/bootstrap.c`, size 70,985 bytes, SHA-256 `1be021e8b8e09642b9336a28d46498c9e8fe486bf595935086fc60f25a72b88b`. This unapproved build has no patch hash compiled in, so it safely chooses official Codex until a separately approved build supplies the patch hash.
- Windows fake-backend tests cover argument and stdio forwarding, exit status, hidden GUI-subsystem launcher, exact receipt gating, and early patched-process fallback. Environment tests cover WindowsApps prior-value retention, refusal to overwrite a manual CLI path, persistent bootstrap staging, and compare-and-swap rollback.
- The official `0.164.0-alpha.11.1` app-server initialize and `config/read` were separately probed with a temporary `CODEX_HOME`; no model request or real credentials were used. The fake-bootstrap test harness injects the official path, so ancestor-process discovery itself is not covered by an automated integration test.
- This work does not install the bootstrap into the current user environment, change a Windows service/task, build the large patched Rust CLI, or emit an OS toast. The desktop launch/ancestry behavior and post-initialize failure recovery still need a real desktop integration test before claiming those guarantees.
