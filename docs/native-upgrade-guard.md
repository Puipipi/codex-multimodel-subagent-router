# Native CLI upgrade guard

`CODEX_CLI_PATH` is installed as a small Win32 GUI-subsystem bootstrap. It is not a Node, batch, or PowerShell launcher. At startup it finds the desktop's official Codex executable from an ancestor `OpenAI.Codex_<package>...\app\Codex.exe` image, then uses that package's `app\resources\codex.exe`. If ancestry cannot be queried, it tries the process package and enumerates registered `OpenAI.Codex_2p2nqsd0c76g0` packages with Windows AppModel APIs, choosing the newest valid install path without assuming `C:\Program Files`. It never treats the inherited `CODEX_CLI_PATH` as the official executable and refuses to recurse into itself. If no registered or accessible official CLI exists, it writes a Chinese disabled status before returning a startup error; a missing/broken desktop installation has no executable for fallback to launch.

The bootstrap selects the isolated patched CLI only when `compatibility.json` has schema 1 and matches the official executable SHA-256, full `codex-cli --version`, exact Windows package version, the patch's compiled-in approved SHA-256, and a successful `app-server-initialize` probe receipt. The patch must be a regular file under `%CODEX_HOME%\router-runtime` (or `%USERPROFILE%\.codex\router-runtime`). The runtime root is derived from the bootstrap's own content-addressed `router-runtime\bootstrap\<sha>.exe` location, with environment/home fallback for direct development launches. Any missing, stale, malformed, or mismatching evidence selects official Codex immediately and writes a local `upgrade-status.json` with a Chinese disabled reason. Status is separate from stdout/stderr so app-server JSON-RPC remains clean.

`native-bootstrap-install.mjs` builds an environment plan that points to a content-addressed bootstrap under `<CODEX_HOME>\router-runtime\bootstrap\<sha256>.exe`. Apply copies it atomically from the plugin's packaged bootstrap, then changes environment values using compare-before-set. The returned journal snapshot includes the prior bootstrap bytes; rollback restores/removes the executable only if its current hash still matches the installed bytes, and restores environment values only if they still match the transaction. A non-WindowsApps user-selected `CODEX_CLI_PATH` without an owned receipt is preserved by refusing the plan.

For each app-server launch, the bootstrap first runs the patched CLI in a separate hidden process with private stdin/stdout pipes, `--listen stdio://`, a throwaway `%TEMP%` working directory and `CODEX_HOME`, and an 1.8-second bound per response. It sends initialize and config/read, requiring syntactically valid JSON responses with matching top-level ids, result objects, expected fields, and the exact recorded CLI version in `userAgent`. EOF, timeout, malformed JSON, version mismatch, or JSON-RPC error terminates the probe and launches the official CLI with the untouched desktop handles and original arguments. Probe output never reaches the desktop stream. Only after a successful probe does it start the patched CLI with the original arguments and desktop handles. Once that live process has received desktop traffic, it is never blindly restarted against the official CLI because the stream may contain non-repeatable requests. A later patched-process failure is reported by the desktop connection; this guard guarantees a clean official fallback before any desktop request is consumed.

The pinned upstream source revision used for the runtime port defines `stdio://` as the app-server stdio transport in [`codex-rs/cli/src/main.rs`](https://github.com/openai/codex/blob/6905ecede7816e91373e9eabda3f6b0368fc747b/codex-rs/cli/src/main.rs#L3114-L3133).

## Status contract

`scripts/native-upgrade-guard.mjs` exports pure selection/status helpers. Status is `{state: "healthy"|"repaired"|"disabled", reason, repairAttempted, updatedAt}`; no credentials or identity material are stored. The native bootstrap writes `healthy` when a verified patch is selected and `disabled` when it falls back. The routing/settings layer must consume this status to disable only the native child role and surface the Chinese reason. This module does not implement a Windows toast or UI notification; it must not be presented as end-to-end notification until that consumer is wired.

## Evidence and limits

- The checked-in bootstrap was built locally with MinGW GCC (`-municode -mwindows -O2 -lbcrypt -lshell32`), source `native/bootstrap/bootstrap.c`; size 73,850 bytes, SHA-256 `93425e3bc86ad85c5d2330ac66b82765a1ce02739e6b0482d16ef1c0697459fd`. This unapproved build has no patch hash compiled in, so it safely chooses official Codex until a separately approved build supplies the patch hash.
- Windows fake-backend tests cover desktop ancestry metadata-to-package resolution (test-only injection), exclusion of test bypasses from release builds, argument and stdio forwarding, exit status, hidden GUI-subsystem launcher, exact receipt gating, and isolated initialize/config/read probes for patched early-exit, garbage, malformed JSON, hang, JSON-RPC error, version mismatch, successful patched handshake, and official fallback. Failure cases assert that the untouched desktop initialize/config/read stream reaches official exactly once and yields only official responses. Environment tests cover WindowsApps prior-value retention, refusal to overwrite a manual CLI path, persistent bootstrap staging, moved-package recovery, manual-change preservation and compare-and-swap rollback.
- The Windows test resolves the actual current desktop package via process ancestry and production package-family lookup, and repeats lookup with parent access disabled to prove registered-package fallback. A test-only package metadata fixture exercises a package on `D:`. Release builds contain no test override switches. The production rollback resolver is also exercised against the current package. If the package is unregistered and its last known official binary is gone, the guard reports the installation unavailable and disables native routing; it cannot manufacture a missing official CLI.
- This work does not install the bootstrap into the current user environment, change a Windows service/task, build the large patched Rust CLI, or emit an OS toast. UI/status consumption and real desktop launch integration remain separate integration work.
