# Native CLI upgrade guard

`CODEX_CLI_PATH` is installed as a small Win32 GUI-subsystem bootstrap. It is not a Node, batch, or PowerShell launcher. At startup it finds the desktop's official Codex executable from an ancestor `OpenAI.Codex_<package>...\app\Codex.exe` image, then uses that package's `app\resources\codex.exe`. If ancestry cannot be queried, it tries the process package and enumerates registered `OpenAI.Codex_2p2nqsd0c76g0` packages with Windows AppModel APIs, choosing the newest valid install path without assuming `C:\Program Files`. It never treats the inherited `CODEX_CLI_PATH` as the official executable and refuses to recurse into itself. If no registered or accessible official CLI exists, it writes a Chinese disabled status before returning a startup error; a missing/broken desktop installation has no executable for fallback to launch.

The bootstrap selects the isolated patched CLI only when `compatibility.json` has schema 1 and matches the official executable SHA-256, full `codex-cli --version`, exact Windows package version, the patch's compiled-in approved SHA-256, and a successful `app-server-initialize` probe receipt. The receipt's probe result is read only from the canonical nested `compatibility` object (`status`, `probe`, and `cliVersion`); top-level mirrors and flat-only receipts are rejected. The patch must be a regular file under `%CODEX_HOME%\router-runtime` (or `%USERPROFILE%\.codex\router-runtime`). The runtime root is derived from the bootstrap's own content-addressed `router-runtime\bootstrap\<sha>.exe` location, with environment/home fallback for direct development launches. Any missing, stale, malformed, or mismatching evidence selects official Codex immediately and writes a local `upgrade-status.json` with a Chinese disabled reason. Status is separate from stdout/stderr so app-server JSON-RPC remains clean.

`native-bootstrap-install.mjs` builds an environment plan that points to a content-addressed bootstrap under `<CODEX_HOME>\router-runtime\bootstrap\<sha256>.exe`. Apply copies it atomically from the plugin's packaged bootstrap, then changes environment values using compare-before-set. The returned journal snapshot includes the prior bootstrap bytes; rollback restores/removes the executable only if its current hash still matches the installed bytes, and restores environment values only if they still match the transaction. When rollback owns the current bootstrap override, it clears a prior WindowsApps CLI pin even if that old package directory still exists; the desktop app then resolves its currently active package. A non-WindowsApps user-selected `CODEX_CLI_PATH` without an owned receipt is preserved by refusing the plan.

`native-bootstrap-maintenance.mjs` exports `observeApiBackend({bootstrapPath,runtimeDir,...})`, `armApiBootstrap({runtimeDir,runtimeRoot,bootstrapSourcePath,adapter,...})`, and `disarmOwnedBootstrap({journalPath,adapter})`. Arm and disarm share a file lock at `<router-runtime>\bootstrap-install.json.lock` across probes, journal and environment changes. The C bootstrap's `--bootstrap-capabilities` and `--bootstrap-observe-backend` modes are read-only and emit JSON to stdout. Observation walks the caller's real Windows parent chain to the nearest `codex.exe`, hashes that file, then the Node gate compares it with the exact verified runtime manifest. Only call this observation from an exec tool that runs under the model-host process; an MCP server's ancestry may describe a different process. Arming requires the runtime manifest and bootstrap's compiled allowlist/source/version to agree, resolves the official CLI through the bootstrap's registered-package resolver, verifies the official CLI and desktop package versions, and probes the patched CLI with isolated initialize/config/read. The probe receipt is staged in a temporary directory and installed at `<router-runtime>\compatibility.json`, the path the C bootstrap reads. The API-owned `bootstrap-install.json` records the prior receipt bytes and deployed hash alongside the bootstrap file and environment CAS values. Failed setup and disarm restore/delete those files only while their installed hashes are still owned; later manual receipt edits are preserved. Arming then CAS-applies only `CODEX_CLI_PATH`. It does not write the legacy DeepSeek journal or change other environment values. Arming reports `restartRequired: true`; the later model-host process observation is the only signal that the API backend is actually active. Disarm clears only `CODEX_CLI_PATH` while it still matches this journal's value and preserves a later manual edit.

In the bootstrap capabilities payload, the historically named `approvedPatchHashes` list contains approved **compiled `codex.exe` SHA-256 values**. The source patch digest remains separately bound by `runtime-manifest.json` as `patch_sha256`; maintenance checks the capability list against `binary_sha256`, and the compatibility receipt writer checks the same executable hash.

For each app-server launch, the bootstrap first runs the patched CLI in a separate hidden process with private stdin/stdout pipes, `--listen stdio://`, a throwaway `%TEMP%` working directory and `CODEX_HOME`, and an 1.8-second bound per response. It sends initialize and config/read, requiring syntactically valid JSON responses with matching top-level ids, result objects, expected fields, and the exact recorded CLI version in `userAgent`. EOF, timeout, malformed JSON, version mismatch, or JSON-RPC error terminates the probe and launches the official CLI with the untouched desktop handles and original arguments. Probe output never reaches the desktop stream. Only after a successful probe does it start the patched CLI with the original arguments and desktop handles. Once that live process has received desktop traffic, it is never blindly restarted against the official CLI because the stream may contain non-repeatable requests. A later patched-process failure is reported by the desktop connection; this guard guarantees a clean official fallback before any desktop request is consumed.

The pinned upstream source revision used for the runtime port defines `stdio://` as the app-server stdio transport in [`codex-rs/cli/src/main.rs`](https://github.com/openai/codex/blob/6905ecede7816e91373e9eabda3f6b0368fc747b/codex-rs/cli/src/main.rs#L3114-L3133).

## Status contract

`scripts/native-upgrade-guard.mjs` exports pure selection/status helpers. Status is `{state: "healthy"|"repaired"|"disabled", reason, repairAttempted, updatedAt}`; no credentials or identity material are stored. The native bootstrap writes `healthy` when a verified patch is selected and `disabled` when it falls back. The routing/settings layer must consume this status to disable only the native child role and surface the Chinese reason. This module does not implement a Windows toast or UI notification; it must not be presented as end-to-end notification until that consumer is wired.

## Evidence and limits

- The checked-in bootstrap was built locally with MinGW GCC (`-municode -mwindows -O2 -lbcrypt -lshell32`), source `native/bootstrap/bootstrap.c`; size 116,686 bytes, SHA-256 `f40b57a4fa179358ffda716df60a9d13f9157d7c74744ee8e54ae65267146d02`. Its capabilities report an empty approved-patch allowlist and empty source/version build metadata, so maintenance refuses to arm it. The fake compile-time metadata fixture verifies capability output, but is test-only and is not packaged.
- Windows fake-backend tests cover desktop ancestry metadata-to-package resolution (test-only injection), exclusion of test bypasses from release builds, argument and stdio forwarding, exit status, hidden GUI-subsystem launcher, exact receipt gating, and isolated initialize/config/read probes for patched early-exit, garbage, malformed JSON, hang, JSON-RPC error, version mismatch, successful patched handshake, and official fallback. Failure cases assert that the untouched desktop initialize/config/read stream reaches official exactly once and yields only official responses. Environment tests cover clearing retained or removed WindowsApps prior pins on rollback, refusal to overwrite a manual CLI path, persistent bootstrap staging, manual-change preservation and compare-and-swap rollback.
- The Windows test resolves the actual current desktop package via process ancestry and production package-family lookup, and repeats lookup with parent access disabled to prove registered-package fallback. A test-only package metadata fixture exercises a package on `D:`. The read-only observer was also run against the actual current desktop process chain and reported `C:\Program Files\WindowsApps\OpenAI.Codex_26.1021.3705.0_x64__2p2nqsd0c76g0\app\resources\codex.exe` with SHA-256 `1103e9e09c71fa2cd0afd6d8f3b9a2d63174fe8efd7cb5bd09f1cb14ef58a098`. Release builds contain no test override switches. If the package is unregistered and its last known official binary is gone, the guard reports the installation unavailable and disables native routing; it cannot manufacture a missing official CLI.
- This work does not install the bootstrap into the current user environment, change a Windows service/task, or emit an OS toast. API maintenance has not been activated in the user's environment; Task4 still needs to wire its signatures and status handling. The checked-in bootstrap cannot arm the 0.164 runtime until a separately reviewed release build compiles in that patch's allowlist, source commit, and runtime version after the upstream CLI artifact is approved.
