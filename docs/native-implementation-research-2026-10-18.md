# Codex 原生 DeepSeek 子代理方案源码调研

观察日期：2026-10-18。以下结论来自固定提交的公开源码与已下载测试；未运行候选项目、未构建 Codex、未发模型请求，也未验证真实桌面 UI。`[源码]` 表示在对应固定提交中直接核对；`[文档]` 表示仓库作者说明；`[推断]` 表示对本项目适用性的判断。

## 结论

当前候选都不能直接满足“Sol 主会话直连 OpenAI，同时 DeepSeek 是 Codex 原生 child、不经额外 GPT 解密/转译、压缩可靠且故障隔离”。**[推断/推荐]** 最接近目标的底座仍是 upstream Codex 原生协作机制，加一个仅对明确 DeepSeek child 生效的 provider 与 `ModelsManager` 隔离补丁，并单独处理 child 任务明文传递。OpenCodex 的压缩路由和测试、DSCodex 的受控摘要封装、codex-router 的证据来源校验可以借鉴；它们整体都要求 Responses 代理或改变压缩协议，不能代替底座补丁。

上游当前 main 与项目 pinned commit 在 child manager 的关键处一致：`Session::spawn` 收到 `Arc::clone(&self.models_manager)`，并未按 child role/provider 建立独立 manager。[源码：pinned `thread_manager.rs` 第 2326–2334 行](https://github.com/openai/codex/blob/4ebc485ca321243727539187169425fcf972f2c4/codex-rs/core/src/thread_manager.rs#L2326-L2334)；[源码：current main `thread_manager.rs` 第 2338–2347 行](https://github.com/openai/codex/blob/ce0323f2f2d3b25e82806cd555237da3db4e1897/codex-rs/core/src/thread_manager.rs#L2338-L2347)。pinned 的模型窗口状态读取 `TurnContext.model_info()` 的 auto-compact limit 与 context window（第 26–50、61–95 行），因此 child 的 manager/catalog 元数据隔离是窗口阈值正确性的前置条件；这不能通过调 `comp_hash` 替代。[源码](https://github.com/openai/codex/blob/4ebc485ca321243727539187169425fcf972f2c4/codex-rs/core/src/session/session_context_window.rs#L26-L50)。

另一个独立协议边界是 remote compaction v2：pinned Rust 收流后要求恰好一个 `compaction` output（第 375–475 行，尤其 464–467），其 `encrypted_content` 必须符合 Codex/OpenAI 后端契约；DeepSeek 原生 Responses 是否能提供可被接受的同等产物，现无本研究中的真实 API 证据。[源码](https://github.com/openai/codex/blob/4ebc485ca321243727539187169425fcf972f2c4/codex-rs/core/src/compact_remote_v2.rs#L375-L475)。第四个问题又不同：v2 native-to-routed `NEW_TASK` 可作为外部 provider 无法读取的加密内容。OpenCodex 文档明确给出此限制及 v1/明文 `agent_message` 方向，但这是代理项目的说明，不能证明本地补丁已打通所有 Codex 协作消息类型。[文档](https://github.com/lidge-jun/opencodex/blob/6936d9885d8a9bda9301737affcbaf1a4ff00e17/docs-site/src/content/docs/guides/sub-agent-surface.md#L165-L190)。

这四项须分别验收：child manager 决定所用模型的上下文/自动压缩元数据；`comp_hash` 是模型切换时的兼容标记（上游另行比较旧、新 `comp_hash` 并产生 `CompHashChanged` 原因，见 [`session_turn.rs`](https://github.com/openai/codex/blob/ce0323f2f2d3b25e82806cd555237da3db4e1897/codex-rs/core/src/session/session_turn.rs#L1425-L1455)）；加密 `NEW_TASK` 决定任务文本是否能到达 DeepSeek；remote compaction blob 决定 Codex 能否接受压缩结果。修复其中一项不意味着其余项已解决。

## 可复用点与推荐

1. **保留 upstream 原生协作底座。** 在明确 `native_deepseek` child role 路径选择独立 provider 与 child `ModelsManager`，使 child 的 model catalog/context limit/auto-compact metadata 一致；父 Sol/Luna 的 provider、模型发现及正常 OpenAI 直连保持不变。不要只从 child config 设 provider，却继续让 child session 使用父 manager。
2. **把任务可读性作为独立 wire contract。** 仅在选中 DeepSeek 子代理的请求序列化/回包解析处，为协作工具 namespace 与已验证函数名使用外部兼容别名或安全明文协议；保留内部 canonical 工具名、授权/沙箱策略及原生 UI 事件。别把全局 `multi_agent_v2` 或所有子代理内容改成明文。OpenCodex v1/v2 文档与明文 v2 opt-in 可作兼容性参考，不是直接集成实现。
3. **保留原生 compact 契约，先验证后启用。[推断/推荐]** 候选方向是让 child 专属 DeepSeek provider 声明“不支持 remote compaction”，由 Codex 选择本地摘要；这不是已验证的上游保证。仍需核实本地压缩执行、保存后恢复、真实 1M metadata 阈值及 `comp_hash` 模型切换行为。若 Codex 强制要求 remote v2 的 `encrypted_content`，不能把 `ocx1:`、DSCodex 私有 AES 封装或 `kcr2:` 冒充 OpenAI 密文。不得用 GPT proxy 解密/重包来假称 DeepSeek 原生直连。
4. **失败隔离。** DeepSeek 请求只走独立 provider 和有界超时；超时明确失败，不向 OpenAI/GPT 自动转发、不重放已发送任务，也不影响父会话状态。这些属性要用 child/UI/app-server 集成验收确认，不从各候选 README 推断。

**[推断/推荐]** 现阶段可复用 OpenCodex 的 provider 身份检查与压缩回归测试结构、DSCodex 的 child-route 模型状态隔离思想、codex-router 的来源 ID 校验；最终实现仍需基于 upstream native child。当前仓库已有的 child-only manager 补丁尚未 Rust 编译；真实 app-server compact、自动压缩、重启恢复、Windows 桌面面板与模型请求均未在本调研中验证。把 `comp_hash=null` 用于 unknown routed model 仅解决兼容性判定，不提供 1M 窗口元数据，也不解密协作 task。
